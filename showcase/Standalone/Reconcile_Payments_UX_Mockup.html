Implementation Notes

  • Button relocation uses existing CSS utilities — the new two-row layout uses flex__row, flex__justify-end, and button__red--small classes already defined in the PLAT-781 design system. No new CSS required.
  • Post Receipts promotion to green uses the pre-existing button__green class (#2CB475). This class was already built for the design system but not used on this screen.
  • "Type DELETE" confirmation is built using the existing BootstrapDialog library's custom message and getButton().disable()/enable() API. No new dependencies needed.
  • Payment count display requires two new read-only AJAX endpoints (GET /reconcile_payments/unposted_counts and unposted_post_counts) that mirror the exact query logic from the existing DeleteUnpostedPaymentsJob. Counts are fetched fresh on each button click.
  • Report type dropdown replaces the current radio buttons. The controller's print_reports action already dispatches based on a report_type param. For "both", the JS submits two sequential AJAX requests — one for summary, one for detail — reusing the existing PrintReconcilePaymentsSummaryJob and PrintReconcilePaymentsDetailJob without modification. Each report gets its own BillingJob record and appears separately in reprints.
  • All changes apply to both screens: the main Reconcile Payments and the Reconcile Lien Payments screen. The lien screen additionally migrates from legacy Bootstrap classes (btn-primary, btn-danger) to the new design system.

Business Rules & Design Rationale

Why force "Summary & Detail" for non-self reconciliation?
When reconciling your own payments, you already have context — you know what you entered. A summary may be enough. But when reconciling someone else's payments (another cashier, a system source, or "All"), you're acting as a reviewer/auditor. The Detail report is required to verify individual transactions, not just trust the totals. This follows the same principle behind separation of duties in accounting — the person reviewing should have more information than the person who entered.
Why move the Delete button to a separate lower row?
This creates three levels of cognitive separation between daily workflow buttons and the destructive action: (1) different visual group/row, (2) right-aligned vs. left-aligned, (3) smaller size. Fitts's Law tells us that targets further from the cursor's resting position are harder to hit accidentally. The lower-right corner is the maximum distance from "Get Report" on the upper-left. One confirmed accidental deletion has already occurred with the current layout.
Why "type DELETE" instead of just OK/Cancel?
This is a "friction pattern" — intentionally adding a small barrier before irreversible actions. GitHub uses it for repository deletion, AWS for resource termination. The key is that it doesn't block power users who know what they're doing, but it completely eliminates accidental clicks. Combined with showing the actual count of affected payments and accounts, users make an informed decision rather than blindly confirming. The current dialog says "ALL unposted payments" but never tells you how many.
Why promote Post Receipts to green?
Post Receipts is the primary daily action — the culmination of the reconciliation workflow. Yet it was styled as gray/secondary, making it the least visible button on the screen while the rarely-used Delete was the most visible (red). Green signals "go" / "positive action" and correctly positions Post Receipts as the intended next step after reviewing the report. The visual flow now reads: Get Report (blue, "do this first") → Post Receipts (green, "then do this").
Why remind about PDF generation before posting?
Once payments are posted, they can no longer be changed or deleted. The reconciliation report serves as the pre-posting audit trail. If a user posts without generating the report first, they lose the ability to verify the batch contents against their physical records. The reminder in the confirmation dialog catches this before it's too late.
Why "Summary & Detail" in one click?
The current workflow requires 6 interactions to get both reports (select Summary → Get Report → wait → select Detail → Get Report → wait). The new dropdown reduces this to 3 interactions (select "Summary & Detail" → Get Report → wait once). Both PDFs are stored as separate entries in the reprints list for individual access later. No existing job code needs modification — we simply trigger both from the client side.
