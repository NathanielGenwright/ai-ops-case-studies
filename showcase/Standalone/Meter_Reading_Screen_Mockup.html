Implementation Notes

  • Customer context bar reuses the existing customer header partial (_customer_header). The data is already loaded on every customer-scoped page.
  • Meter context bar pulls from the @meter model already loaded by the controller. Zero additional queries.
  • CSS Grid replaces <table> for the readings list. The three-zone layout uses grid-template-columns: 1fr 200px 80px. Each zone is independently styled.
  • Stacked reading pairs use flex-direction: column within a grid cell, halving the column count (4 → 2 visual units).
  • Color-coded badges use the existing MetroBill design system badge classes. New badge variants (estimated, highflow, unbilled) follow the same .badge--{variant} pattern.
  • Action icons consolidate 3 columns into 1. Delete uses "reveal on intent" (gray → red on hover), same Fitts's Law principle from the Reconcile Payments redesign.
  • Hover-to-expand notes are CSS-only: .secondary-note:hover { white-space: normal; }. No JavaScript required.
  • Live consumption calculation on Enter/Edit screens can use a small JS snippet: endReading - startReading on input change. No AJAX needed.
  • Delete modal replaces the browser data-confirm with a BootstrapDialog that fetches reading details via an AJAX call to the existing show action.
  • Form tile layout on Edit screen uses CSS Grid grid-template-columns: 1fr 1fr. No new controller actions needed — same form fields, different visual grouping.
  • Warning banner on Final Reading is a static HTML element, no logic required. It's always shown when on the final reading screen.
  • All screens share the same CSS — design tokens, button classes, tile components, form styles. This mockup is a single file specifically to prove that consistency.

Business Rules & Design Rationale

Why a workflow-connected mockup instead of isolated screens?
Staff don't use screens in isolation — they flow through a sequence: find the meter, check readings, enter or edit one, occasionally delete. Designing each screen independently leads to inconsistent patterns (different button placements, different context displays, different form layouts). A connected workflow mockup ensures every screen uses the same components, the same context bars, the same button hierarchy.
Why three zones on the readings list?
Staff scanning meter readings have a clear priority: "What's the usage?" first, then "anything unusual?", then "who and notes?" only when investigating. The flat table treats all 14 columns equally, forcing the eye to hunt. The three-zone layout matches actual scanning behavior: glance left (operational), check right when needed (metadata), act far-right (edit/delete).
Why make Usage the hero metric?
Usage determines the bill amount. It's the single most-referenced value. Yet it got the smallest column (75px) and the same visual weight as "Days" or "Entered By." Bold blue styling lets staff scan usage values vertically — like accountants scanning a ledger column.
Why a delete modal instead of "Are you sure?"
The browser's confirm dialog says "Are you sure?" but doesn't tell you what you're deleting. When staff have a list of readings on screen, accidentally clicking Delete on the wrong row means losing data with no way to verify. The custom modal shows the full reading detail (values, date, usage, who entered it) so the user can confirm they're deleting the right record.
Why a warning banner on the Final Reading screen?
Closing a meter changes its status to Inactive and has downstream billing implications. The current screen looks identical to Enter Reading but with a different button label. Staff may not realize "Close Old Meter" does something fundamentally different from "Save Reading." The warning banner makes the consequence explicit before they reach the button.
Why tile the Edit form instead of one long list?
The current Edit screen is a single-column list of 12+ fields. Staff editing a reading value have to scroll past billing options and notes to find the fields they need. Tiling groups related fields: Reading Data (the values they're here to fix), Billing Options (status and flags), and Adjustments/Notes (supplementary). Each tile is independently scannable.
Why a live consumption calculation?
Currently, consumption shows as a dash until the reading is saved. Staff have to save, check the result, and edit again if something looks wrong. Live calculation provides immediate feedback — if a user types "10529390" instead of "1052939" (extra zero), the consumption will show an obviously wrong value before they save. This catches typos at the source.
Why group actions on the meter card instead of scattered links?
The current Meters screen has "View Readings" and "Replace Meter" as text links in different locations. Staff have to hunt for the right link. Grouping all meter actions (View, Enter, Replace) as buttons on the meter card creates a clear "what can I do with this meter?" answer in one place.
